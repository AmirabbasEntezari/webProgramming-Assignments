# تمرین Git 

## سؤال ۱: merge و rebase

هر دو برای این هستند که کار یک branch را وارد branch دیگر کنیم، ولی راهشان فرق دارد.

### git merge
 تغییرات دو branch را با هم ترکیب می‌کند و اگر دو branch از هم جدا شده باشند یک کامیت merge جدید می‌سازد که دو والد دارد. کامیت‌های قبلی دست‌نخورده می‌مانند. نتیجه‌اش این است که تاریخچه شاخه‌شاخه می‌شود و می‌شود دید که چه موقع کار از هم جدا و دوباره یکی شده.

### git rebase
 کامیت‌های branch فعلی را برمی‌دارد و یکی‌یکی روی آخرین کامیتِ branch مقصد دوباره اعمال می‌کند. چون پایه‌ی کامیت‌ها عوض می‌شود، Git کامیت‌های جدید با hash جدید می‌سازد و قدیمی‌ها کنار گذاشته می‌شوند. تاریخچه خطی می‌شود، انگار از اول کار را بعد از آخرین تغییرات مقصد شروع کرده بودیم. در rebase ممکن است conflict چند بار و برای هر کامیت جدا پیش بیاید، ولی در merge فقط یک بار حل می‌شود.

مثال برای merge: feature تمام شده و می‌خواهم وارد `main` مشترک کنم. چون merge تاریخچه را بازنویسی نمی‌کند، برای بقیه‌ی تیم مشکلی پیش نمی‌آید.

```bash
git switch main
git merge feature
```

مثال برای rebase: روی یک branch شخصی که هنوز push نکرده‌ام کار می‌کنم و در این فاصله `main` جلو رفته. قبل از اینکه کارم را بفرستم، روی `main` rebase می‌کنم تا تاریخچه تمیز باشد و کامیت merge اضافه نداشته باشم.

```bash
git switch feature
git rebase main
# اگر conflict شد: رفعش، بعد
git add <file>
git rebase --continue    # یا git rebase --abort برای انصراف
```

نکته‌ی مهم این است که روی کامیت‌هایی که قبلاً push شده و دیگران گرفته‌اند نباید rebase کرد، چون تاریخچه عوض می‌شود و باید force push بزنیم.

## سؤال ۲: انتخاب بخشی از تغییرات

در خروجی `git diff` تغییرات هر فایل به تکه‌های جدا تقسیم شده که هر کدام با خطی مثل `@@ -12,7 +12,9 @@` شروع می‌شود. به هر کدام از این تکه‌ها یک hunk می‌گویند: چند خط اضافه یا حذف‌شده به‌همراه چند خط اطرافش برای زمینه. اعداد بالای آن می‌گویند این تکه از کدام خط شروع می‌شود و در نسخه‌ی قدیم و جدید چند خط است.

برای اینکه فقط بعضی از hunkها را stage کنیم:

```bash
git add -p notes.py
```

(با `--patch` هم همین کار را می‌کند.) Git هر hunk را نشان می‌دهد و می‌پرسد stage شود یا نه. گزینه‌های مهمش:

- `y`: این hunk را stage کن
- `n`: stage نکن
- `s`: hunk را به تکه‌های کوچک‌تر بشکن
- `e`: hunk را دستی ویرایش کن، برای وقتی که حتی یک hunk هم چند کار مختلف دارد
- `a` و `d`: همه‌ی hunkهای باقی‌مانده‌ی این فایل را stage کن یا نکن
- `q`: خارج شو


```bash
git diff --staged
git commit -m "Fix validation bug"
```

فایده‌اش این است که اگر در یک فایل چند کار نامرتبط انجام داده باشم (مثلاً رفع یک باگ، عوض کردن فرمت و یک print برای debug)، می‌توانم هر کدام را در کامیت جدا بگذارم. کامیت‌های کوچک و منسجم خواندن تاریخچه، revert کردن و پیدا کردن باگ را راحت‌تر می‌کنند و چیزهای موقتی هم به‌اشتباه کامیت نمی‌شوند.

## سؤال ۳: git bisect

bisect یک جست‌وجوی دودویی روی تاریخچه است برای پیدا کردن کامیتی که باگ را وارد کرده. هر بار Git یک کامیت از وسط بازه‌ی مشکوک را checkout می‌کند، من تست می‌کنم و می‌گویم سالم است یا معیوب، و بازه نصف می‌شود. برای n کامیت تقریباً log₂(n) مرحله کافی است.

مراحل:

```bash
git bisect start
git bisect bad            
git bisect good v1.0    
```

بعد از این Git یک کامیت وسطی را checkout می‌کند. برنامه را اجرا می‌کنم و نتیجه را اعلام می‌کنم:

```bash
git bisect good    
git bisect bad
```

این کار را تکرار می‌کنم تا Git بنویسد `<hash> is the first bad commit`. در آخر برای برگشتن به وضعیت اول:

```bash
git bisect reset
```

اگر اسکریپتی داشته باشم که با کد خروج ۰ برای سالم و غیرصفر برای معیوب تمام شود، کل کار را خودکار می‌کند:

```bash
git bisect run ./test.sh
```

مثال: تست `test_login` الان fail می‌شود ولی یک ماه پیش سالم بود و بین این دو ۱۲۸ کامیت هست. به‌جای اینکه دستی یکی‌یکی بررسی کنم، با bisect در حدود ۷ مرحله به کامیت مقصر می‌رسم.

مفید است چون سریع است، لازم نیست حدس بزنم باگ از کجا آمده، و دقیقاً خودِ کامیت را نشان می‌دهد، یعنی می‌توانم ببینم چه چیزی عوض شده. اگر کامیت‌ها کوچک باشند (مثل سؤال ۲) نتیجه خیلی دقیق‌تر است.

## سؤال ۴: بررسی تغییرات پیش از کامیت

**۱. دستورها**

```bash
git status
git diff
git diff --staged     # یا --cached
```

`git status` هم staged و هم unstaged و هم untracked را نشان می‌دهد. در این سناریو `README.md` همزمان در دو بخش «Changes to be committed» و «Changes not staged for commit» دیده می‌شود.

`git diff` تغییرات working tree را با staging area مقایسه می‌کند، یعنی ویرایش‌هایی که بعد از `git add` انجام داده‌ام. `git diff --staged` ناحیه‌ی staging را با آخرین کامیت مقایسه می‌کند، یعنی همان چیزی که در کامیت بعدی ثبت می‌شود.

**۲. کامیت بدون `-a`**

فقط تغییراتی که staged شده‌اند وارد کامیت می‌شوند. ویرایش‌های بعد از `git add` در working tree می‌مانند و بعد از کامیت هم در `git diff` دیده می‌شوند. دلیلش این است که کامیت از محتوای index ساخته می‌شود و نه از فایل روی دیسک. (با `-a` فایل‌های tracked تغییرکرده قبل از کامیت خودکار stage می‌شدند و ویرایش دوم هم می‌رفت.)

**۳. نادیده گرفتن پوشه‌ی tmp**

در `.gitignore` در ریشه‌ی مخزن می‌نویسم:

```gitignore
/tmp/
```

اسلش اول یعنی فقط پوشه‌ی tmp در ریشه و اسلش آخر یعنی این یک پوشه است. بعد خود `.gitignore` را هم add و commit می‌کنم تا برای هم‌تیمی‌ها هم کار کند. اگر فقط برای خودم بخواهم، می‌شود در `.git/info/exclude` نوشت که کامیت نمی‌شود.

برای فایلی که قبلاً tracked شده این کافی نیست، چون `.gitignore` فقط روی فایل‌های untracked اثر دارد. باید ردیابی فایل را متوقف کنم:

```bash
git rm --cached path/to/file
git commit -m "Stop tracking file"
```

با `--cached` فقط از index حذف می‌شود و فایل روی دیسک می‌ماند.

## سؤال ۵: conflict هنگام merge

**۱. چرا conflict شد؟** چون من و هم‌تیمی‌ام هر دو یک خط مشخص را که در کامیت مشترک یک متن داشت به دو متن مختلف تغییر داده‌ایم و Git نمی‌داند کدام را نگه دارد. این به آن معنی نیست که هر تغییری در یک فایل conflict می‌سازد. اگر دو نفر خط‌های مختلفی را عوض کنند، Git خودش ترکیبشان می‌کند. اگر هر دو هم دقیقاً یک تغییر یکسان بدهند conflict نمی‌شود. فقط وقتی conflict داریم که تغییرها روی یک ناحیه باشند و با هم فرق داشته باشند.

**۲. پیدا کردن فایل‌ها**

```bash
git status
git diff --name-only --diff-filter=U
```

در `git status` فایل‌ها در بخش «Unmerged paths» با برچسب `both modified` می‌آیند. داخل فایل Git نشانگر می‌گذارد:

```text
<<<<<<< HEAD
متن branch فعلی (main)
=======
متن branch که merge می‌کنم (description-feature)
>>>>>>> description-feature
```

بین `<<<<<<<` و `=======` نسخه‌ی branch فعلی است و بین `=======` و `>>>>>>>` نسخه‌ی branch دیگر. این نشانگرها فقط برای این هستند که ببینم دو نسخه کجا هستند و باید قبل از کامیت پاک شوند.

**۳. مراحل رفع**

```bash
git switch main
git merge description-feature     
git status
```

بعد `README.md` را باز می‌کنم، متنی می‌نویسم که اطلاعات هر دو نسخه را داشته باشد و هر سه خط نشانگر را پاک می‌کنم. برای اینکه مطمئن شوم چیزی از نشانگرها نمانده:

```bash
git grep -nE '^(<<<<<<<|=======|>>>>>>>)' README.md
git diff --check
```

اگر `git grep` خروجی نداشته باشد یعنی چیزی نمانده. بعد:

```bash
git add README.md
git status                        
git commit                         
```

**۴. لغو merge**

```bash
git merge --abort
```

چون قبل از merge همه‌چیز commit شده بود و working tree تمیز بود، این دستور مخزن را دقیقاً به حالت قبل از merge برمی‌گرداند.

## سؤال ۶: بازگرداندن تغییرات

**۱. دور انداختن تغییرات unstaged یک فایل**

```bash
git restore notes.txt
```

(روش قدیمی‌تر: `git checkout -- notes.txt`.) محتوای فایل از index، که با آخرین کامیت یکی است، دوباره نوشته می‌شود و ویرایش‌هایم از بین می‌روند. staging، تاریخچه و فایل‌های دیگر تغییر نمی‌کنند. فقط باید حواسم باشد که این کار برگشت‌پذیر نیست، چون این تغییرات جایی ثبت نشده بودند.

**۲. خارج کردن فایل از staging و نگه داشتن ویرایش‌ها**

```bash
git restore --staged notes.txt
```

(قدیمی‌تر: `git reset HEAD -- notes.txt`.) نسخه‌ی index برابر آخرین کامیت می‌شود، پس فایل از staging خارج می‌شود. ولی working tree دست‌نخورده می‌ماند و ویرایش‌هایم هنوز هستند و فایل دوباره در بخش «not staged» دیده می‌شود. تاریخچه تغییری نمی‌کند.

**۳. کامیت اشتباهِ push‌شده روی main**

```bash
git revert <hash>
git push origin main
```

`git revert` یک کامیت جدید می‌سازد که دقیقاً عکس تغییرات کامیت اشتباه است. کامیت اصلی در تاریخچه می‌ماند ولی اثرش خنثی می‌شود.

چرا reset و `push --force` مناسب نیست: این کار تاریخچه‌ی مشترک را بازنویسی می‌کند. هم‌تیمی‌ها کامیت اشتباه را قبلاً گرفته‌اند، پس تاریخچه‌ی محلی‌شان با remote نمی‌خواند و موقع pull به مشکل و conflict می‌خورند. علاوه بر این، force push ممکن است کامیت‌هایی را که بقیه بعد از آن روی remote گذاشته‌اند پاک کند. با revert تاریخچه فقط جلو می‌رود، برای همه امن است و معلوم می‌ماند چه اتفاقی افتاده و چه چیزی برگردانده شده.
